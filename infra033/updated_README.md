## Summary

**Part A: a crash.** `diskreport`, a tiny C program, printed two disks and then died with `Segmentation fault (core dumped)` (it tried to read memory it isn't allowed to). Linux saved a **core dump**, a 440 KB snapshot of the program's memory at the moment it died. **`gdb`** (the standard debugger for C) read it after the fact. The **backtrace** (the chain of functions running at the crash) showed:
- The crash happened inside `strlen`, the C library's "how long is this text?" function.
- The **bug** was two frames up, in our own code: the third disk had **no name** (`name = 0x0`), and our code passed it to `strlen` anyway.

A one-line check fixed it.

**Part B: how Ubuntu packages carry fixes.** `apt source chrony` downloaded chrony 4.8's original code plus Ubuntu's packaging:
- `debian/changelog` records who changed what and why. Ubuntu's own change to chrony is about **containers**, like `k8s1`.
- `debian/patches/` holds 4 patches applied on top, in the order listed in `series`.
- Each patch starts with a standard header (DEP-3): what it does, who wrote it, and which bug it relates to.

## Why

Many low-level tools are written in C: the Linux kernel, `systemd`, `chrony`, much of Ceph and Open vSwitch. When one crashes in production, you usually get a **core file** afterwards, not a live crash. Reading it with `gdb` is a core skill for sustaining and escalation roles. And customer fixes often ship as patches inside Ubuntu packages, so knowing where they live is part of the job.

## Runbook (with real results)

All commands ran on **`mc1`**.

## Part A: The crash

### Step 1: Install the tools, and build the program

```bash
sudo apt-get install -y gcc gdb
mkdir -p ~/drill-033 && cd ~/drill-033
# diskreport.c written (3 disks; the third is {NULL, 92})
gcc -g -O0 -Wall -o diskreport diskreport.c
```
Built with no warnings.
- `-g`: debug information (line numbers, variable names) for `gdb`.
- `-O0`: no optimisation, so the program runs line by line as written.
- `-Wall`: all common warnings. **None fired.** The compiler can't know the data will hold a `NULL` when the program runs.

### Step 2: Turn on core dumps (temporarily)

```bash
cat /proc/sys/kernel/core_pattern | tee ~/drill-033/core_pattern.orig
sudo sysctl -w kernel.core_pattern=/tmp/core.%e.%p
ulimit -c unlimited
```
The original pattern (see Step 6) hands crashes to **apport**, Ubuntu's crash reporter. It was switched to plain files in `/tmp`, and `ulimit -c unlimited` allowed core files in this terminal.

### Step 3: Symptom

```bash
./diskreport; echo "exit code: $?"
ls -lh /tmp/core.diskreport.*
```
```
sda    45%
sdb   100%
Segmentation fault         (core dumped) ./diskreport
exit code: 139
-rw------- 1 nicky nicky 440K Oct 17 10:02 /tmp/core.diskreport.32384
```
- Two disks printed fine; it died on the third.
- `139` = 128 + 11, where **11 is the signal number for a segmentation fault** (`SIGSEGV`). The kernel stopped the program.
- The core file is named after the program and its process ID (`32384`), as the pattern asked. It's readable only by its owner (`-rw-------`), because core files can hold sensitive data from memory.

### Step 4: Diagnose with gdb (reading the core file)

```bash
gdb -q -batch \
  -ex "bt" \
  -ex "frame 1" -ex "p name" \
  -ex "frame 2" -ex "p *d" \
  -ex "frame 3" -ex "p i" \
  ./diskreport /tmp/core.diskreport.*
```
```
This GDB supports auto-downloading debuginfo from the following URLs:
  <https://debuginfod.ubuntu.com>
Enable debuginfod for this session? (y or [n]) [answered N; input not from terminal]
...
Core was generated by `./diskreport'.
Program terminated with signal SIGSEGV, Segmentation fault.
#0  __strlen_avx2 () at ../sysdeps/x86_64/multiarch/strlen-avx2.S:76
warning: 76     ../sysdeps/x86_64/multiarch/strlen-avx2.S: No such file or directory
#0  __strlen_avx2 () at ../sysdeps/x86_64/multiarch/strlen-avx2.S:76
#1  0x00005b8b57500185 in name_length (name=0x0) at diskreport.c:17
#2  0x00005b8b575001b8 in report (d=0x5b8b57503040 <disks+32>) at diskreport.c:22
#3  0x00005b8b57500212 in main () at diskreport.c:28

#1  ... in name_length (name=0x0) at diskreport.c:17
17          return strlen(name);
$1 = 0x0
#2  ... in report (d=0x5b8b57503040 <disks+32>) at diskreport.c:22
22          printf("%-*s %3d%%\n", name_length(d->name) + 2, d->name, d->used);
$2 = {name = 0x0, used = 92}
#3  ... in main () at diskreport.c:28
28              report(&disks[i]);
$3 = 2
```
**Reading the backtrace, bottom to top:**

| Frame | Function | What it shows |
|---|---|---|
| `#3` | `main` | `i = 2`: the loop was on the **third** disk (counting from 0) |
| `#2` | `report` | that disk is `{name = 0x0, used = 92}`: **no name** |
| `#1` | `name_length` | our code passed `name=0x0` to `strlen`, at line 17 |
| `#0` | `__strlen_avx2` | the crash itself, inside the C library, reading text at address `0x0` |

> **Key lesson: frame `#0` is where it crashed, not where the bug is.** `strlen` is fine; it's used by nearly every program. Our code handed it a `NULL`. Walk up the backtrace to the first frame that's **your** code.

**Other details:**
- `avx2` in `__strlen_avx2`: the C library picks the fastest version of `strlen` for the CPU, here one using the AVX2 instructions.
- `No such file or directory`: `gdb` has no source for the C library, which is normal.
- **debuginfod:** Ubuntu's `gdb` offered to download debug details for system libraries from `debuginfod.ubuntu.com`. Saying yes would show the C library's source lines too. That's useful when a crash really is inside a system library.

### Step 5: Fix and prove it

```bash
sed -i 's|    return strlen(name);|    return name ? strlen(name) : 0;|' diskreport.c
sed -i 's|...printf line...|...d->name ? d->name : "(unnamed)"...|' diskreport.c
gcc -g -O0 -Wall -o diskreport diskreport.c && ./diskreport; echo "exit code: $?"
```
```
sda    45%
sdb   100%
(unnamed)  92%
exit code: 0
```
- `name ? strlen(name) : 0` means "if there's a name, measure it; otherwise use 0".
- A missing name now prints as `(unnamed)`. All 3 disks are reported, and the program exits cleanly (`0`).

### Step 6: Restore the core dump setting

```bash
sudo tee /proc/sys/kernel/core_pattern < ~/drill-033/core_pattern.orig
cat /proc/sys/kernel/core_pattern
sudo rm -f /tmp/core.diskreport.*
```
```
|/usr/share/apport/apport -p%p -s%s -c%c -d%d -P%P -u%u -g%g -F%F -- %E
```
Back to the original: crashes go to **apport** again. The `|` at the start means "send the core dump to this program" instead of writing a file.

## Part B: How Ubuntu packages carry fixes

### Step 7: Enable source packages and download chrony's source

```bash
sudo sed -i 's/^Types: deb$/Types: deb deb-src/' /etc/apt/sources.list.d/ubuntu.sources
sudo apt-get update -q
sudo apt-get install -y dpkg-dev
cd ~/drill-033 && apt source chrony
ls
```
```
chrony-4.8  chrony_4.8-2ubuntu1.debian.tar.xz  chrony_4.8-2ubuntu1.dsc  chrony_4.8.orig.tar.gz  ...
```
| File | What it is |
|---|---|
| `chrony_4.8.orig.tar.gz` | chrony's **original** code, as its authors released it |
| `chrony_4.8-2ubuntu1.debian.tar.xz` | the **packaging**: the `debian/` folder with patches, changelog and build rules |
| `chrony_4.8-2ubuntu1.dsc` | the description file tying them together, with checksums |
| `chrony-4.8/` | the two unpacked together, with patches applied |

The version `4.8-2ubuntu1` reads: chrony **4.8**, Debian's packaging revision **2**, then Ubuntu's **1st** change on top.

### Step 8: Read the packaging

```bash
cd ~/drill-033/chrony-*/
head -12 debian/changelog
ls debian/patches/
cat debian/patches/series
head -20 debian/patches/$(head -1 debian/patches/series)
```

**Reading it:**
- **`resolute`** is the Ubuntu release this package was built for, which means `mc1` runs that release.
- **Ubuntu's change is about containers.** Inside a container, chrony can't set the clock. Ubuntu made chrony keep running and keep serving time to others (the `-x` option) instead of failing. `LP #1589780` is the Launchpad bug that asked for it. This is exactly the situation in this lab's LXD containers.
- **`LP: #...`** numbers are Launchpad bugs, Ubuntu's bug tracker. That's how a customer's report links to the fix that ships.
- **`series`** lists the 4 patches in the order they're applied.
- **The patch header (DEP-3)** says what it does (`Description`), who wrote it (`Author`), the related bug (`Bug-Debian`), and whether it was sent to chrony's own authors (`Forwarded: not-needed`, because it only skips a flaky test). Below the header, `-` lines are removed and `+` lines added.

```bash
cd ~ && rm -rf ~/drill-033
sudo sed -i 's/^Types: deb deb-src$/Types: deb/' /etc/apt/sources.list.d/ubuntu.sources
sudo apt-get update -q
```

## Incident write-up (Part A)

| | |
|---|---|
| **Symptom** | `diskreport` printed 2 of 3 disks, then `Segmentation fault (core dumped)`, exit code `139` |
| **What I checked** | Core file (440 KB) read with `gdb`. Backtrace: crash in `__strlen_avx2` (C library), called from `name_length(name=0x0)` (line 17) in `report`, for the disk `{name = 0x0, used = 92}`, loop index `i = 2` |
| **Root cause** | The third disk entry had no name (`NULL`), and the code passed it to `strlen` without checking |
| **Fix** | Check for `NULL` before using the name (`name ? strlen(name) : 0`), and print `(unnamed)` instead. All 3 disks reported, exit code `0` |
| **Prevention** | Check data that may be missing before using it. Keep core dumps collectable in production (apport or `systemd-coredump`) so crashes can be read after the fact. Build with `-g` (or ship separate debug symbols) so backtraces show names and line numbers |

**Lessons:**
1. **Frame `#0` is where it crashed, not where the bug is.** Walk up to your own code.
2. **A core file is a crash you can read later.** No need to catch it live.
3. **`(core dumped)` needs two settings:** a place to put the core (`core_pattern`) and permission to write one (`ulimit -c`).
4. **Fixes ship as patches with a paper trail:** changelog entry, patch header, bug number.

**AWS comparison:** on EC2 the core dump setup is the same Linux setting. For Lambda or managed services you don't get core files; you get logs and traces (CloudWatch, X-Ray), which is why self-managed Linux skills like this matter in infrastructure support.

## Retention Check

The backtrace's top frame (`#0`) was inside `strlen`, a C library function used by millions of programs. Why wasn't that the bug, and how did you find the real one?

**Answer:** `strlen` did exactly what it's meant to: it read the text it was given. It was given address `0x0` (`NULL`), which can't be read, so it crashed. The bug was in the caller. Walking up the backtrace, frame `#1` showed our `name_length` passing `name=0x0`, and frame `#2` showed the disk entry with no name.
